# 本机备份与恢复

星工坊底部的「给记忆留一份备份」覆盖**全部空间**，不是仅当前空间。创建后会显示本机路径、时间、大小和消息数；可以再次检查完整性，或恢复为独立副本。页面只列出最近 20 份应用管理的备份，更早的仍保存在目录中。

## 备份内容

每份备份是一个目录，必须整体保存：

```text
备份目录/
  xingxi.sqlite   # 一致的 SQLite 数据快照，无需原实例的 WAL 文件
  manifest.json  # 格式、创建时间、校验和、数据库结构摘要与记录数量
```

包含空间设定、原始资料、知识及修订、关系、全部聊天、MCP 固定绑定、召回开关、派生索引、任务和回答参考。不包含 `secrets.json`、`access-token`、附件目录、其他本机文件或项目源代码。聊天或资料里自行粘贴的秘密仍属于正文，会随数据库备份；备份不是自动脱敏文件，也没有额外加密。

备份默认写到当前数据目录的 `backups/<随机 UUID>/`。可手动将**整个备份目录**复制到自己选择的存储介质；应用不会上传或同步它。应用管理目录中未完成、没有有效清单的目录不会显示为成功备份。

## 用命令行创建与验证

需要 Node.js 22.16+（22.x）或 24+。在项目目录执行，路径替换为自己的位置；创建目标必须不存在，其父目录必须存在。

```sh
npm run backup -- create /absolute/path/to/new-backup
npm run backup -- verify /absolute/path/to/new-backup
```

创建可在服务运行时进行，使用 SQLite 在线备份而非只复制主文件，包含完成提交的 WAL 数据。其他连接持续大量写入时，复制可能重新开始，因此不能保证包含“点击瞬间”或“返回瞬间”的全部消息；结果是复制期间一个一致的已提交状态。单任务最长等待 10 分钟，超时不报告任务成功；请先检查列表中是否已有完整发布的备份，再降低写入频率重试。

CLI 可指定任意新备份目录；界面只管理自己创建的 UUID 目录。CLI 使用 `XINGXI_DATA_DIR` 选择来源，默认项目 `.local`。校验不会请求模型，SHA-256 用于检测文件变化，不是对备份作者身份的签名。

## 恢复与核对

界面「恢复为独立副本」会写入当前数据目录下新的 `restored-<UUID>/`，并提供启动命令。恢复先复制、检查复制后的校验和、数据库结构、完整性、外键和聊天索引对应关系，再将临时文件改名为正式数据库。不覆盖当前实例；失败不会发布一个可用数据库文件。

也可指定新目录：

```sh
npm run backup -- restore /absolute/path/to/new-backup --to /absolute/path/to/new-data
```

目标必须不存在，即使是空目录也拒绝覆盖。恢复副本没有模型 Key 和旧访问令牌。首次启动会生成新令牌，资料阅读与 MCP 检索可用；需要模型回答时重新配置 Key。备份中曾在运行的提炼任务会在启动时标记为中断，可以手动重试。

macOS / Linux，在项目目录启动副本：

```sh
XINGXI_DATA_DIR='/absolute/path/to/new-data' XINGXI_NO_SEED=1 PORT=4182 npm start
```

Windows PowerShell：

```powershell
$env:XINGXI_DATA_DIR='C:\absolute\path\to\new-data'
$env:XINGXI_NO_SEED='1'
$env:PORT='4182'
npm start
```

打开 `http://127.0.0.1:4182/`。核对空间、聊天、知识历史和「本轮参考」。如要把副本作为正式实例，先停止旧服务，再用期望的端口启动副本；不要将恢复文件直接覆盖到正在运行的数据库上。保持新数据目录即可，无需把旧 `.local` 删除或改名。

MCP 客户端也要连接副本：

```json
{
  "mcpServers": {
    "xingxi": {
      "command": "node",
      "args": ["/absolute/path/to/xingxi-workspace/server/mcp.mjs"],
      "env": {
        "XINGXI_DATA_DIR": "/absolute/path/to/new-data",
        "XINGXI_URL": "http://127.0.0.1:4182"
      }
    }
  }
}
```

使用原 `spaceId` / `sessionId`，或原 `session_open` 的 `binding`，即可恢复相同会话身份。不同路径的 MCP 客户端应配置同一个目标目录和端口，不要复制原实例令牌过去。

## 校验边界

当前恢复接受本版结构，以及上一发布版（1489440）的精确已知结构。旧版副本先按原清单校验，再在新目录中执行本地增量迁移，添加摘要表与索引；原备份不改变。其他结构不匹配时，请使用创建备份时的项目版本恢复，再按项目迁移流程升级。不会执行清单中提供的 SQL，也不会接受额外触发器或任意数据库结构。保留创建备份时的项目版本记录，有助于未来升级。

创建、校验、恢复在独立工作线程中运行，一次只处理一项页面任务；其成本仍随数据库大小增长并竞争磁盘资源，不能保证其他操作完全无抖动。校验覆盖物理完整性、外键、已知结构和聊天索引的 ID/作用域对应；不证明资料真实或所有派生文本的语义准确。恢复测试还会核对消息序号、绑定、搜索结果与参考快照。

删除当前实例的消息不会追溯修改已有备份，恢复旧备份也会恢复当时存在的消息。这是独立快照的语义；不需要的备份由你在文件系统中管理。失败或进程被强制终止时可能留下未发布的临时目录，不能将它当成成功的恢复结果。
